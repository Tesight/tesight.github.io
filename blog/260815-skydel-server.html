Skydel Client & Server 工作流程

从源码梳理 Skydel Remote API 的命令通道、API 版本握手、指令封包与响应匹配，以及 ClientHil 的车辆信息接收与 ECEF/NED 动态数据推送流程

源码地址：skydelsdx/remotesimulator.py

建立连接：RemoteSimulator.connect()

获取 API 版本：getServerApiVersion()

在 getServerApiVersion() 方法中，整个流程可以分为发送请求和等待响应两步。

发送请求

上述过程构造了一个 2 + 1 + 4 字节的请求包，由 socket 发送：

msg_len: unsigned short | MsgId.ApiVersion: unsigned char | ApiVersion: unsigned int

实际上，通过 API 与 Skydel Server 通信时，收发的数据包都遵循这个格式：

消息标识 + 消息内容的数据长度0：指令消息
1：指令执行的结果消息
2：API 查询消息		发送或接收的真正数据

等待响应的过程与 getServerApiVersion() 等待响应的过程类似，不过其中多了对响应的 UUID 与发送指令的 UUID 匹配的要求。_handleException() 方法根据响应结果判断了 Skydel Server 的状态，决定是否要抛出异常。

post() 与 call()

Skydel API 给用户提供了两种发送指令的方法，分别是 post() 和 call()。实际上两个命令都是在调用 _postCommand() 这个核心方法，而不同之处在于 call() 在调用 postCommand() 后会立即调用 _waitCommand()，其中的 while 1== 1 会导致程序阻塞，直至拿到指令的响应或是与 Server 断开连接。在调用 post() 后则需要手动调用 wait() 才能拿到指令的响应。

ClientHil

在 RemoteSimulator.connect() 的最后，由指令获取到的 HIL 端口实例化了一个 ClientHil 类，打开了 HIL 客户端。ClientHil 同样继承了 Client 类，主要用于在 HIL 模式中向 Skydel Server 推送实时的坐标位置。

消息类型

ClientHil 定义了 7 种消息类型标识（MsgId）：

消息类型标识意义
Hello向 Skydel Server 握手
Bye向 Skydel Server 挥手
VehicleInfoSkydel Server 发来的车辆信息
PushEcef向 Skydel Server 推送车辆位置信息
PushEcefNed向 Skydel Server 推送车辆位置 + 姿态信息
PushEcefDynamics向 Skydel Server 推送车辆位置 + 运动信息
PushEcefNedDynamics向 Skydel Server 推送车辆位置 + 姿态 + 运动信息

pollVehicleInfo()

该方法的主要功能是从 socket 中查询接收车辆信息数据，若有则解析并返回；若无数据则返回 None。socket 在接收数据时有超时时间，若 socket 中没有已到达的数据，socket 就会在超时时间内等待网络数据的到来（阻塞等待）。pollVehicleInfo() 的主要操作是将 socket 的超时时间设置为 0（self.sock.settimeout(0)），不论是否获取到数据都立刻返回。避免在监控车辆状态这样频繁检查数据、实时性要求高的场景下发生主线程的阻塞。

整体流程是：

  1. sim.beginVehicleInfo() 令 Skydel Server 开始发送车辆信息
  2. sim.start() 开始仿真
  3. sim.lastVehicleInfo() 获取最新的车辆信息，可以显示或写入日志
  4. sim.stop() 停止仿真
  5. sim.endVehicleInfo() 令 Skydel Server 不再发送车辆信息
  6. sim.disconnect() 与 Skydel Server 断开连接
